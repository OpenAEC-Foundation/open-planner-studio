# CI, auto-update en releases

CI (`.github/workflows/`): `ci.yml` draait de stappen van `npm run verify` — via `scripts/verify-parts.mjs` verdeeld over parallelle jobs (`static`, `planning`, `suites` en de browsersuite in vier shards, verdeeld op gemeten duur per spec via `--duration-shard` (`scripts/browser-shards.mjs`); een niet-ingedeelde nieuwe stap valt vanzelf in `static`, en `static` controleert dat de matrix elk deel draait en dat de browsershards samen `1/n` … `n/n` zijn), met een afsluitende job `test` die alleen groen is als alle delen groen zijn — plus `tauri build --no-bundle` op Ubuntu/Windows/macOS; `live.yml` deployt de browserbuild (`dist/`) naar `open-planner-studio.open-aec.com` bij elke push naar `main` — de webbuild is een echte productie-deploy, geen dev-target — zonder eigen verify: het draait via `workflow_run` pas ná een geslaagde `ci.yml`-run op `main` (dus ook ná de Tauri-builds) en alleen voor precies de commit die CI testte — is `main` intussen verder, dan slaat die run over en deployt de nieuwere push zelf; een eigen seriële verify haalde de 45 min niet meer (2026-10-13), geen `workflow_dispatch` (zou ongepoort deployen; opnieuw deployen = "Re-run all jobs"); `release.yml` bouwt installers op `v*`-tags achter diezelfde gate plus een controle dat de tag overeenkomt met de gebumpte versie, en `snap.yml` volgt daarna via `workflow_run` (zie *Auto-update & releases* verderop in dit bestand). Een rode suite blokkeert dus zowel de deploy als de release; draai gerichte checks lokaal en laat de volledige `npm run verify` in CI lopen (open een concept-PR en kijk met `gh pr checks --watch`; zie AGENTS.md). `release-verify.yml` controleert een gepubliceerde release op schone runners (Linux 22.04/24.04 + Fedora, Windows, macOS): updater-`.sig`'s, `latest.json` en digests via `scripts/verify-release.mjs`, installeren, starten met een alive-check, Authenticode (`Get-AuthenticodeSignature`, `signtool`) en Developer ID/Gatekeeper/notarisatie. `release.yml` draait datzelfde script vóór publicatie op de draft (`--draft-id`); bij een FOUT blijft de release een draft. Streng na "Build and Release" (`workflow_run`), bij `release: published` en `workflow_dispatch`; bij een PR op de workflow of de scripts in rapportmodus tegen de laatste release (zie `docs/release-verificatie.md`). `release: published` vuurt niet na `release.yml`, want die publiceert met `GITHUB_TOKEN`. `headless-api.yml` test de headless API (`headless/server/`): server lokaal en als container met de smoke-test, plus `cfn-lint` op `deploy/aws/ecs-fargate.yaml`; hij draait op elke push naar `main` en op PR's die `src/`, de kernbouw, `headless/`, `deploy/aws/` of de lockfile raken, en zit bewust niet in `verify` (Docker en Python horen niet in de lokale poort; zie `docs/headless-api.md`). `mcpb.yml` bouwt de Claude Desktop-bundel (`npm run build:mcpb`) en controleert het manifest met de vastgezette officiële CLI (`mcpb validate`); hij draait op elke push naar `main` en op PR's die de bundel raken, en zit niet in `verify` (de CLI wordt gedownload). `release.yml` doet dat ook in de job `build-mcpb` en zet `open-planner-studio-<versie>.mcpb` als asset op de draft; `publish-release` wacht erop. Daarnaast bestaan `download-stats.yml` (wekelijks, publiceert de JSON naar de `stats`-branch), `label-sync.yml` (`.github/labels.json` → GitHub-labels; een nieuw label hoort in `labels.json`), `triage-new-issues.yml` en `auto-assign-issues.yml` (zie `docs/agents/issue-tracker.md`). `verify:audit` zit sinds 2026-09-03 bewust **niet** meer in die keten: een nieuw gepubliceerd advisory zette anders élke push en deploy rood, ook een die de dependency niet raakt (gemeten: de releasecommit van v2026.9.0 op `browserslist`). Dependabot security alerts staan aan op de repository en zijn het meldkanaal; een advisory wordt in een eigen commit opgelost, `npm run verify:audit` blijft daarvoor als los commando bestaan.

## Auto-update & releases

Versies volgen `JJJJ.W.N`: ISO-weekjaar, ISO-weeknummer zonder voorloopnul, volgnummer binnen de week vanaf 0. `npm run bump` leest actuele origin-tags met `git ls-remote --tags origin 'v*'` en neemt het hoogste volgnummer van die week uit de tags én de huidige versie plus 1 (of begint bij `.0` als beide ontbreken). Een onbereikbare of ontbrekende origin stopt de bump vóór er wordt geschreven, zonder terugval op lokale tags. `OPS_BUMP_DATE=JJJJ-MM-DD` maakt de datum injecteerbaar. Een expliciet nummer blijft mogelijk en mag niet lager zijn dan de huidige versie. Het script houdt `package.json`, de twee rootvelden in `package-lock.json`, `src-tauri/tauri.conf.json`, `Cargo.toml`, het eigen pakket in `Cargo.lock`, beide headless-`package.json`-bestanden, de OpenAPI-documentversie, `snap/snapcraft.yaml` en `integrations/claude-desktop/manifest.json` gelijk. `build-core.mjs` leidt de kernversie af van `package.json`. De release-gate controleert al deze velden tegen de tag met `bump-version.js --check`. Rond nieuwjaar telt het ISO-weekjaar: 1 januari 2027 is `2026.53.N`, 4 januari is `2027.1.0`. De volledige runbook staat in de **`release`-skill** (`.claude/skills/release/`) — draai die bij een release in plaats van de stappen los te herhalen; een `v*`-tag is onomkeerbaar en auto-update naar alle gebruikers. Besluit eigenaar, gesprek 2026-10-22: de wekelijkse zaterdagjob op aia09-mp50 voert de skill volledig automatisch uit, zonder menselijk akkoord vóór de tag. Release-flow: onafgerond werk voor de laatste tag hervatten → open release-PR/ongetagde versie op main alleen hervatten als die numeriek hoger is dan de nieuwste origin-tag, zonder nieuwe bump → anders wijzigingscontrole en groene main → `npm run bump` zonder argument → notes, Engelse changelog, vijf highlights in 28 talen en UI-vertalingen → release-PR en groene CI → zelf squashmergen → groene CI op de exacte main-SHA → tag `v*` → push. `verify:translations`, `verify` en ontbrekende releasetekst blokkeren de tag tot herstel. Verkeerde origin of geen wijzigingen en geen hervatwerk blijven stopregels. Besluit 8, eigenaar, gesprek 2026-10-22: rode main-/release-PR-CI of releaseworkflow eerst eenmaal herhalen met `--failed`; blijft hij rood, dan de kleinste fix-PR vanaf main, een tweede Sol-review (`codex`/`gpt-6.1-sol`, `reasoningEffort: xhigh`, letterlijke reviewerbrief, BLOKKEERT/VERVOLG), groene PR-CI, zelf mergen met `--merge --admin` en groene CI op de exacte main-SHA. Uitzondering: cijfercorrecties squashen met `--squash --admin`, met cijfers voor precies één extra commit vanaf actuele main. De zaterdagjob stopt uiterlijk 14:00 Europe/Amsterdam; open fixes blijven staan en de volgende zaterdag hervat dezelfde voortgang. Een bestaande tag wordt nooit verplaatst, verwijderd of opnieuw gepusht. Aanvullend besluit orkestrator, 2026-10-22: vereist herstel gewijzigde getagde code/workflow, dan fix op main via dezelfde reviewroute, tag afschrijven met de vaste regel in de release-PR en nooit meer hervatten; een draft blijft draft. De job maakt zonder bestaande opvolgkandidaat met `npm run bump` zonder argument een nieuwe versie met de oorspronkelijke releasetekst plus fix en doorloopt alle poorten. Het hervatpad slaat een afgeschreven tag over, maar behoudt hem als `PREV` voor `VERSION > PREV`; de deadline blijft gelden. Wiki en uitsluitend de twee website-releaseblokken gaan elke release mee; andere gidsvertalingen alleen op afzonderlijk verzoek. Websitebesluit, orkestrator na vraag aan eigenaar, 2026-10-22: website-PR direct mergen met `--merge --admin`, daarna een geslaagde `deploy.yml` op de merge-SHA of een bewezen afstammeling en beide blokken live controleren. Ontbrekende/geannuleerde runs: controleer opvolgruns, anders eenmaal `gh workflow run deploy.yml --repo OpenAEC-Foundation/website` binnen het zaterdagmandaat. Een blijvende websitefout laat de app-release staan, blokkeert de volgende app-release niet en wordt de volgende zaterdag naast de nieuwe release hervat en gerapporteerd. De poorten en CI vervangen menselijke review; `release.yml` bouwt en signeert installers (Windows via Azure Artifact Signing tijdens het bundelen: `scripts/windows-sign.ps1 -Setup` schrijft een `--config`-override met `bundle.windows.signCommand`, zodat Tauri programma, uninstaller en installer tekent; alleen release.yml en `windows-sign-check.yml` laden die override, `ci.yml`/`tauri:dev` tekenen niet; `windows-sign-check.yml` bewijst het zonder tag op een PR die `release.yml` of het script raakt; macOS universal, met `app`-target voor de updater, getekend en genotariseerd; `macos-sign-check.yml` bewijst dat zonder tag op een PR die `release.yml` of de macOS-scripts raakt, en laat de dmg 7 dagen als artifact staan) en publiceert `latest.json`; `snap.yml` verpakt daarna de release-`.deb` tot Snap (`snap/snapcraft.yaml`) en publiceert 'm — sinds 2026-07-30, met het secret `SNAPCRAFT_STORE_CREDENTIALS` (zie `docs/release-secrets.md`) — ook automatisch naar het `stable`-kanaal van de Snap Store; dat gebeurt bij elke `v*`-tag en is, net als de rest van een release, onomkeerbaar. De in-app updater checkt stil bij het opstarten (`App.tsx` → `updaterService`, `UpdateDialog`): endpoint is de GitHub-release-`latest.json`, geverifieerd met de minisign-pubkey in `tauri.conf.json`; Snap- en AUR-installs slaan de stille update-check en in-app installatie over (snapd respectievelijk pacman werkt bij); AppImage, `.deb` en Windows/macOS gebruiken de in-app updater (detectie via het `install_kind`-command: `appimage`/`snap`/`aur`/`deb`/`native`). Ná een geslaagde update toont `JustUpdatedDialog` één keer wat er nieuw is: `ui.justUpdated` wordt gezet door de versievergelijking tegen de bewaarde `ops-lastVersion`, en `src/services/updater/releaseInfo.ts` haalt de release-omschrijving, het grootteverschil en de tijd tussen releases op bij de GitHub Releases-API (pure functies, headless getest in `tests/planning/check-just-updated.ts`).

De webbuild levert daarnaast `public/release-highlights.json` mee — gegenereerd uit de catalogus met `npm run gen:release-highlights-json`, bewaakt door `npm run verify:release-highlights-json` en geserveerd op `https://open-planner-studio.open-aec.com/release-highlights.json` als bron voor de releasetijdlijn op open-aec.com.

**Releaseteksten hebben één bron.** `docs/release-notes/v<versie>.md` bevat alleen de "What's New"-inhoud; `scripts/release-notes.mjs` maakt daar de twee vormen van die de release nodig heeft: `--format=body` (markdown + het vaste Downloads-blok) voor de GitHub-releasepagina, en `--format=notes` (platte tekst — de updater-dialoog rendert geen markdown) voor het `notes`-veld in `latest.json`. `release.yml` roept dat op twee plekken aan: `create-release` voor de body, en `publish-release` voor `latest.json` vlak vóór publicatie. Ontbreekt het bestand, dan valt alles terug op het oude gedrag (generieke body, leeg `notes`-veld) en logt de gate een warning — een vergeten notesbestand breekt de release niet.

## AUR-pakket

`aur.yml` volgt een geslaagde `release.yml` (zoals `snap.yml`), vult `packaging/aur/PKGBUILD` in, test met `makepkg` + `namcap` in een `archlinux`-container en pusht naar de AUR alleen met het secret `AUR_SSH_PRIVATE_KEY`. De jobvoorwaarde weigert vóór checkout elke `workflow_run` uit een andere bronrepo of een ander bronevent dan `push` (met `v*`-prefix) en `workflow_dispatch`; de run moet geslaagd zijn. Wijzig het pakket in `packaging/aur/`, niet in de AUR-git.
