### i18n

27 locales (`nl, en, fr, de, es, zh, it, pt, pl, tr, ar, ja, ko, fa, ru, uk, cs, sk, sr, hr, bg, hu, ro, sv, nb, da, fi`) via `react-i18next`, configured in `src/i18n/config.ts`; each locale has four namespaces (`common`, `task`, `report`, `menu`). Alleen Engels wordt eager geladen; de rest komt lazy binnen via `loadLocale()` (Vite splitst per taal een eigen async chunk), dus vertalingen zijn niet synchroon beschikbaar direct na een taalwissel. `ar` and `fa` are RTL — `RTL_LOCALES` drives `document.documentElement.dir`. `sr` is Servisch in Cyrillisch schrift; de browsertaal `no`/`nn` kiest `nb`. De dertien talen vanaf `ru` staan eerst met Engels als tijdelijke inhoud; de vertaalstraat (`npm run translate`) vult ze, en in die talen telt een sleutel zonder bron-hash in `i18n/ui-sources/` als ontbrekend. i18n initializes and falls back to **English** (`lng`/`fallbackLng: 'en'`); on startup `initLocale()` picks the saved preference, otherwise the OS/browser locale — it is not hard-defaulted to one language. The project's *working* language is Dutch, though: code comments, commit messages, and the canonical source translations are Dutch. Always go through `t(...)`; never hard-code visible text. De typecheck controleert elke sleutel, ook een samengestelde met een vaste set waarden; zet er nooit een `as 'a.b'` op (dat zet de controle uit en `verify:i18n` weigert het) — geef de bron het type `ParseKeys<…>` uit i18next (recept `docs/recepten/i18n-sleutel.md`). Een nieuwe of gewijzigde tekst zet je met `npm run i18n:add` in `nl` + `en` (verplicht); andere talen mogen ontbreken en vallen terug op `en`, de vertaalstraat vult ze aan (besluit B5, 2026-10-10; zie `docs/recepten/i18n-sleutel.md`). Een release eist alles: `npm run verify:translations` (niet in `verify`, wel in `release.yml` en de release-skill) faalt bij elke ontbrekende, verouderde of hashloze vertaling; alle locale-bestanden volgen de vaste opmaak van `npm run i18n:fmt` (één sleutel per regel, volgorde van `nl`), wat `verify:i18n` controleert. Na een `git merge` waarbij beide kanten locale-bestanden raakten: `npm run i18n:resolve` (per sleutel samenvoegen; git kan een verwijderde sleutel "zonder conflict" terugbrengen).

`npm run verify:i18n` (onderdeel van `npm run verify`) eist dat `en` compleet is; in de andere talen is een helemaal ontbrekende sleutel(familie) een rapport (exit 0), een **halve** meervoudsfamilie een fout. Hij bewaakt dat iedere reeds als meervoudfamilie vastgelegde sleutel per locale de juiste **CLDR-pluralcategorieën** heeft, niet alleen letterlijk dezelfde suffixen als `nl`: `zh`/`ja`/`ko` kennen geen `one`, terwijl `pl` (`few`/`many`) en `es`/`fr`/`it`/`pt` (`many`) extra categorieën eisen. De algemene controle leidt echter niet uit een kale aanroep `t(key, { count })` af dat een nog ongesufficete vertaalsleutel een familie moet worden; domeinchecks moeten dat gebruik expliciet bewaken. Voor de taakgrid-registerlabels doet `check-task-grid-i18n.ts` dat door de echte count-aanroepen te inventariseren en de exacte `Intl.PluralRules`-categorieën per locale te eisen. Zulke domeinchecks volgen B5: in een andere taal dan nl/en mag een sleutel of hele familie ontbreken, maar wat er staat moet kloppen (een halve familie is rood). Een ontbrekende pluralvorm valt in i18next **niet** terug op `_other` maar op het Engels — dus een gat is zichtbare taalvervuiling, geen cosmetiek. Voor `es`/`fr`/`it`/`pt` is `_many` (alleen 1.000.000, 2.000.000, …) in dit project gelijk aan `_other`, omdat `{{count}}` altijd in cijfers wordt weergegeven en niet in compacte vorm.
