# De backupmap openen via het eigen Rust-command `open_backup_folder` + `tauri-plugin-opener` (#1245)

`open()` van `@tauri-apps/plugin-shell` staat met `"shell": { "open": true }` in `src-tauri/tauri.conf.json` alleen de standaard-regex toe (`mailto:`/`tel:`/`https?://`), dus een lokaal pad weigert die. Op Windows opende de knop "Backup-map openen" daardoor niets.

Eerste versie van deze fix startte zelf een programma (`explorer`/`open`/`xdg-open`) vanuit Rust. Review ronde 1 wees twee BLOKKEERTs af: (1) `std::process::Command::new("explorer")` zoekt het programma via PATH, en de NSIS-installatie staat in het schrijfbare gebruikersprofiel waar de webview schrijfrechten heeft — een klik kon zo een ander programma starten; (2) een gecanoniceerd pad draagt op Windows het `\\?\`-voorvoegsel, dat de Windows-shell niet slikt, waardoor de klik stil kon mislukken.

Daarom start het command niets zelf: het gebruikt de officiële opener — `tauri-plugin-opener` 2.7.3 (Cargo-dependency, plugin geregistreerd in `main.rs` met `open_js_links_on_click(false)`, zodat de plugin géén klikhandler voor weblinks in de webview injecteert — de webview mag de bijbehorende `open_url`-aanroep niet doen en de bestaande links hebben eigen afhandeling; zie review ronde 2, punt C). De webview krijgt géén capability voor de opener, dus JS kan de opener-commands niet aanroepen — alleen Rust via `app.opener()`.

Het command `open_backup_folder` (`src-tauri/src/commands/open_backup_folder.rs`) heeft **geen padargument**: Rust bepaalt zelf `<appDataDir>/ai-backups` (`BACKUP_DIR`, gespiegeld aan `BACKUP_ROOT` in `src/services/mcp/backupService.ts`; beide kanten gepind op de literal "ai-backups" in hun eigen test). De controle is `std::fs::symlink_metadata` + `file_type().is_symlink()` weigeren + `is_dir()` eisen, zonder terugval voor onbestaande doelen (review ronde 2, punt A: `metadata` volgde een symlink, waardoor `ai-backups` als link naar een map elders in de thuismap de bestandsbeheerder op dat andere doel kon laten uitkomen). `symlink_metadata` volgt geen links — doc.rust-lang.org/std/fs/fn.symlink_metadata.html ("without traversing symbolic links to a resolved destination file"); op Windows opent std de handle met `FILE_FLAG_OPEN_REPARSE_POINT` (std `sys/pal/windows/fs.rs`, `create_file(FILE_READ_ATTRIBUTES, FILE_FLAG_OPEN_REPARSE_POINT)`) en junctions (`IO_REPARSE_TAG_MOUNT_POINT`) vallen onder `FileType::is_symlink()` (reparse-tag bit `0x20000000`, dat MOUNT_POINT net als SYMLINK zet), dus een junction wordt ook geweigerd. Proef: `symlink_weigert` (cfg(unix)) en `junction_weigert` (cfg(windows), `cmd /C mklink /J`) in het module.

Review ronde 3 wees de resterende TOCTOU af: de opener lost de padnaam opnieuw op op het moment van openen, en de webview had via fs rename/remove de map daartussen kunnen vervangen. Daarom zit de waarborg nu in de capabilities, niet in een controle op het klikmoment: `src-tauri/capabilities/backupmap.json` (alle platforms) zet een deny op `fs:allow-rename` en `fs:allow-remove` voor `$APPDATA/ai-backups` zelf en voor `$APPDATA` zelf — de map zelf, niet wat eronder ligt (backupService verwijdert oude backups en lege submappen, dat blijft werken; mappen boven $APPDATA vallen onder knownbug 1775). Proef: `place_file_backupmap_vervangen_verboden` in `place_file.rs` via de echte capabilities (draait in CI onder het bestaande `cargo test … place_file`-filter in rust-tests.yml; zonder backupmap.json is die proef rood, want fs:default staat rename onder $APPDATA toe). Gelezen in de bron (versies uit Cargo.lock): plugin-fs 2.7.1 `commands.rs` toetst een deny sowohl op het pad zoals meegegeven als op het real path (`resolve_real_path`, commands.rs:1647-1653 en 1673-1725), dat `..`, `.` en een afsluitende slash normaliseert en bestaande paden canonicaliseert; tauri 2.12.3 `src/scope/fs.rs:235-240` matcht patronen met `glob::MatchOptions { require_literal_separator: true, ..Default::default() }` — case-sensitief, ook op Windows — maar de real-path-check vangt hoofdlettervarianten op Windows af omdat `canonicalize` de casing op schijf teruggeeft. `copy_file` (commands.rs:369) is `std::fs::copy`, dus alleen bestanden; rename/remove zijn de enigen die een map kunnen verplaatsen.

Wat de opener op Windows precies krijgt (gelezen in de bron van de lockfile-versies): `Opener::open_path` (tauri-plugin-opener 2.7.3 `src/lib.rs:128-137`) → `open(path, None)` (`src/open.rs:10-17`) → `open::that_detached` (crate `open` 5.3.4 `src/windows.rs:40-95`): bij een map `dunce::simplified(path)` (windows.rs:71, stripst het `\\?\`-voorvoegsel als het pad zonder kan), dan `SHOpenFolderAndSelectItems(folder, Some(&[folder]), 0)` (windows.rs:77 — dezelfde item-ID als map én als te selecteren item), met als terugval `ShellExecuteExW` met verb `explore` en class `folder` (windows.rs:50-65). Dat zijn shell-systeem-API's, geen PATH-opzoeking van een programmanaam. De app geeft het pad expres **niet** gecanoniceerd door.

Bekende grens (review ronde 2, punt B — expres géén fix): op Linux/Unix kiest `open` 5.3.4 het programma op naam uit het PATH (`src/unix.rs`, o.a. `xdg-open`/`gio`); `tauri-plugin-shell` hangt van dezelfde crate af, dus dit geldt voor álle open-aanroepen van de app. Zie knownbugs.md punt 2650.

Frontend: `openBackupFolder()` in `src/services/mcp/backup.ts` maakt de map eerst aan via plugin-fs (`mkdir`, binnen de app-data-scope) en roept dan `invoke('open_backup_folder', {})` aan — zonder pad, ná de mkdir (volgorde getoetst in `tests/mcp/cases-open-folder.ts`). De andere `plugin-shell` `open()`-aanroepen (feedback-URL, update-dialogs) openen alleen `https://`-URL's en blijven op die plugin.

Toetsen: `tests/mcp/cases-open-folder.ts` (headless met nep-`__TAURI_INTERNALS__.invoke`; assert dat `open_backup_folder` met lege args wordt aangeroepen ná `plugin:fs|mkdir`, dat `plugin:shell|open` niet wordt aangeroepen, en dat `BACKUP_ROOT` de literal is) en de unittests in `open_backup_folder.rs` (`backup_dir`, `ensure_existing_dir` incl. symlink-weigering; draaien in CI via `.github/workflows/rust-tests.yml`).

Niet bewezen in deze omgeving: een echte klik op een Windows 11-machine (geen Tauri-build, geen Windows-runner hier) — in het bijzonder welke map de echte klik op elk platform toont. CI bouwt de Rust-kant op alle drie de platforms.
