# De backupmap openen via het eigen Rust-command `open_backup_folder` + `tauri-plugin-opener` (#1245)

`open()` van `@tauri-apps/plugin-shell` staat met `"shell": { "open": true }` in `src-tauri/tauri.conf.json` alleen de standaard-regex toe (`mailto:`/`tel:`/`https?://`), dus een lokaal pad weigert die. Op Windows opende de knop "Backup-map openen" daardoor niets.

Eerste versie van dit fix startte zelf een programma (`explorer`/`open`/`xdg-open`) vanuit Rust. Review (Sol, ronde 1) wees twee BLOKKEERTs af: (1) `std::process::Command::new("explorer")` zoekt het programma via PATH, en de NSIS-installatie staat in het schrijfbare gebruikersprofiel waar de webview schrijfrechten heeft — een klik kon zo een ander programma starten; (2) een gecanoniceerd pad draagt op Windows het `\\?\`-voorvoegsel, dat de Windows-shell niet slikt, waardoor de klik stil kon mislukken.

Daarom nu: het command start niets zelf, maar gebruikt de officiële opener — `tauri-plugin-opener` 2.7.3 (Cargo-dependency, plugin geregistreerd in `main.rs`, géén capability voor de webview zodat JS de opener-commands niet kan aanroepen). Het command `open_backup_folder` (`src-tauri/src/commands/open_backup_folder.rs`) heeft **geen padargument**: Rust bepaalt zelf `<appDataDir>/ai-backups` (`BACKUP_DIR`, gespiegeld aan `BACKUP_ROOT` in `src/services/mcp/backupService.ts`; beide kanten zijn gepind op de literal in hun eigen test), eist via `std::fs::metadata` dat het een bestaande map is en weigert anders — de terugval voor onbestaande doelen is daarmee weg, en het commando accepteert geen bestanden of arbitrary paden.

Wat de opener op Windows precies krijgt (gelezen in de bron van de lockfile-versies): `Opener::open_path` (tauri-plugin-opener 2.7.3 `src/lib.rs:128-137`) → `open(path, None)` (`src/open.rs:10-17`) → `open::that_detached` (crate `open` 5.3.4 `src/windows.rs:40-95`): bij een map `dunce::simplified(path)` (windows.rs:71) — dat stripst het `\\?\`-voorvoegsel als het pad zonder kan — daarna `SHOpenFolderAndSelectItems` (windows.rs:77), met als terugval `ShellExecuteExW` met verb `explore` en class `folder` (windows.rs:50-65). Dat zijn systeem-API's van de shell, geen PATH-opzoeking van een programmanaam. De app geeft het pad **niet** gecanoniceerd door (canonicalize voegt `\\?\` toe); alleen `metadata` (volgt links) controleert dat de map bestaat.

Frontend: `openBackupFolder()` in `src/services/mcp/backup.ts` maakt de map eerst aan via plugin-fs (`mkdir`, binnen de app-data-scope) en roept dan `invoke('open_backup_folder', {})` aan — zonder pad. De andere `plugin-shell` `open()`-aanroepen (feedback-URL, update-dialogs) openen alleen `https://`-URL's en blijven op die plugin.

Toetsen: `tests/mcp/cases-open-folder.ts` (headless met nep-`__TAURI_INTERNALS__.invoke`; assert dat `open_backup_folder` met lege args wordt aangeroepen, `plugin:shell|open` niet, en de map eerst wordt aangemaakt) en de unittests in `open_backup_folder.rs` (`backup_dir`, `ensure_existing_dir`). De unittests draaien nu nog niet in CI: `.github/workflows/rust-tests.yml` runt alleen `cargo test … place_file` en `… launch_files` — gewenste Änderung (niet zelf gepusht): een stap `cargo test --manifest-path src-tauri/Cargo.toml open_backup_folder` erbij.

Niet bewezen in deze omgeving: een echte klik op een Windows 11-machine (geen Tauri-build, geen Windows-runner hier); CI bouwt de Rust-kant op alle platforms.
